# Native HUD callers and test bench (0.8.0)

The game's own HUD lives in the `inkHUDLayer` ink layer. This code sits beside the RPCore HUD driver (`server/hud.lua`), which is unchanged.

## Registry

`shared/native_registry.lua` (server and client) and `web/admin/native_registry.js` (admin panel) are generated by
`tools/gen_native_registry.py <redmod/scripts> [<eventcore dir> [<redmod/metadata.json>]]`. They list the ink layers, native ink
widgets, all 1,099 controllers (113 of them `inkHUDGameController`s) and all 124 blackboard definitions with their fields. Names only: the registry says
what exists in the game, not what Open77 accepts.

## Client callers (`client/native_hud.lua`)

- `EventCore.NativeHud.Caller(name)` returns `function(visible) -> result` for any layer, widget or HUD controller.
- `EventCore.NativeHud.Call({ target | group, action })`: `action` is `show`, `hide`, `status`, `introspect` or `restore`; `group` is `hud` (inkHUDLayer plus every HUD controller) or `verified`.
- Result: `{ ok, accepted?, detail, ms, target, action }`. Also exported as `NativeHudCall`.
- Known to work through `Open77.hud.setVisible`: `health`, `stamina`, `weapon`, `speedometer` (mapped from `healthbarWidgetGameController`, `StaminabarWidgetGameController`, `weaponIndicatorController`/`WeaponRosterGameController`, `speedometerLogicController`/`analogSpeedometerLogicController`). Every other name is passed through unchanged; the result says whether the host accepted it.
- Blackboards are browsable but report `no_host_api`. `introspect` lists what `Open77.hud` actually exposes on your build.
- Optional: set `EventCore.NativeHudConfig.restoreOnStart = true` (shared/widgets.lua) to show the four verified components when EventCore starts. Off by default so RPCore can keep them hidden.

## Test bench (admin panel, global admin only)

Open `/eventcore.admin`, then "HUD test bench". Pick a player (yourself or another), a kind and name, and an action. **Send via server** goes admin -> server -> target client -> result -> viewer; **Run locally** skips the server for comparison. Buttons also hide/show `inkHUDLayer` and sweep every HUD controller.

**Schedule:** one step per line, `<ms> <show|hide|status> <name|hud|verified>`, up to 32 steps, 1-10 loops, 2 schedules per admin. The server validates it and sends it to the client once; the client plays it on its own timers and reports each step, so each one appears in the viewer as it fires. A step with no answer shows as a timeout.

Commands (global admin or console):

- `/eventcore.hud.test <player> <name|hud|verified> <action>`
- `/eventcore.hud.schedule <player> <loops> <at,action,name>...`, e.g. `/eventcore.hud.schedule 1 3 0,hide,inkHUDLayer 2000,show,inkHUDLayer`
- `/eventcore.hud.log [n]`, `/eventcore.hud.cancel`

The server keeps the last 300 events in memory (not persisted). The bench changes only what the target client draws.

## Custom ink widgets (`shared/widgets.lua`, `server/widgets.lua`, `client/widgets.lua`)

For the widgets you design yourself, the way the game builds its HUD: each is mounted in a layer (normally `inkHUDLayer`), optionally under an existing controller, and exposes typed fields.

1. Add the widget to `EventCore.WidgetCatalog` in `shared/widgets.lua` (`mount`, optional `parent`/`inkType`, typed `fields`). `example.meter` is a placeholder.
2. A server resource sets values: export `WidgetSet(player, id, values)` / `WidgetReset(player, id?)` (callers: `rpcore`, trusted persistence callers, `EventCore.HudCallers`), or `/eventcore.widget <player> <id> field=value ...` (`... reset`). EventCore clamps and type-checks every value, remembers the latest per player, and replays it when the client reports ready.
3. The client keeps the values and hands them to adapters: `EventCore.Widgets.RegisterAdapter(id | "*", function(id, values, def, event) ... end)`. An adapter is whatever draws the widget: an RPCore panel, or a game-side companion that mounts the ink widget under `inkHUDLayer`. Other client resources can also listen for the local `widget:changed` event.

Not done: nothing here creates an ink widget in the game by itself. That needs a game-side (REDscript/CET) companion, and the path from that companion to Open77 is still unproven (`docs/client-bridge.md`). With no adapter a widget is tracked only and nothing is drawn.
